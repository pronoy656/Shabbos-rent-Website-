3. Route 2 — PATCH /api/v1/owners/me/notification-pref
Purpose
Upserts (creates or updates) the owner's notification preference. Every field is optional — send only what changed.
Request
http
PATCH /api/v1/owners/me/notification-pref
Authorization: Bearer <token>
Content-Type: application/json
Request Body Schema
ts
{
 channel?: "EMAIL" | "PHONE" | "BOTH";
 notificationEmail?: string | null;  // valid email or null to clear
 notificationPhone?: string | null;  // any string or null to clear
 preferredDay?: "SUNDAY" | "MONDAY" | "TUESDAY" | "WEDNESDAY" | "THURSDAY" | "FRIDAY" | "SATURDAY" | null;
 preferredTime?: string | null;      // must match HH:mm regex e.g. "18:00"
}
NOTE
All fields are optional. The backend uses a Zod schema with .optional() / .nullable() on all fields. Sending only { channel: "PHONE" } is valid.
Example Body — Save All Settings
json
{
 "channel": "BOTH",
 "notificationEmail": "owner@shabbosrent.com",
 "notificationPhone": "+9720501234567",
 "preferredDay": "THURSDAY",
 "preferredTime": "18:00"
}
Example Body — Update delivery method only
json
{
 "channel": "EMAIL"
}
Example Body — Clear phone number
json
{
 "notificationPhone": null
}
Validation Rules
Field
Rule
notificationEmail
Must be valid email format if provided
preferredTime
Must match HH:mm (24-hour) — e.g. "06:00", "18:00", "23:59"
channel
Must be exactly "EMAIL", "PHONE", or "BOTH"

6. React Query Hooks
Add these hooks (e.g. hooks/useOwnerNotificationPref.ts):
ts
// hooks/useOwnerNotificationPref.ts
import { useQuery, useMutation, useQueryClient } from "@tanstack/react-query";
import {
 getMyNotificationPref,
 updateMyNotificationPref,
} from "@/services/ownerService";
import type { UpdateNotificationPrefPayload } from "@/types/owner";
/** Query key — used for cache invalidation */
export const NOTIFICATION_PREF_KEY = ["owner", "notification-pref"] as const;
/** Fetches current owner's notification preferences */
export const useMyNotificationPref = () =>
 useQuery({
   queryKey: NOTIFICATION_PREF_KEY,
   queryFn: getMyNotificationPref,
   staleTime: 1000 * 60 * 5, // cache for 5 minutes
 });
/** Saves / updates notification preferences */
export const useUpdateNotificationPref = () => {
 const queryClient = useQueryClient();
 return useMutation({
   mutationFn: (payload: UpdateNotificationPrefPayload) =>
     updateMyNotificationPref(payload),
   onSuccess: () => {
     // Invalidate the GET cache so the UI re-fetches fresh data
     queryClient.invalidateQueries({ queryKey: NOTIFICATION_PREF_KEY });
   },
 });
};

7. Wiring Into the Notification Pref UI Component
This is a minimal wiring example — plug it into your existing component without changing the UI structure:
tsx
// Example: NotificationPrefForm.tsx (wiring only — don't change your existing UI)
import { useMyNotificationPref, useUpdateNotificationPref } from "@/hooks/useOwnerNotificationPref";
import type { UpdateNotificationPrefPayload, DayOfWeek, NotificationChannel } from "@/types/owner";
export function NotificationPrefForm() {
 const { data: pref, isLoading } = useMyNotificationPref();
 const { mutate: savePref, isPending, isSuccess, isError } = useUpdateNotificationPref();
 // --- Map your existing form state to the payload on save ---
 const handleSave = () => {
   // Build payload from your existing form state
   const payload: UpdateNotificationPrefPayload = {
     channel: yourFormState.deliveryMethod as NotificationChannel, // "EMAIL" | "PHONE" | "BOTH"
     notificationEmail: yourFormState.reminderEmail || null,
     notificationPhone: yourFormState.reminderPhone || null,
     // preferredDay and preferredTime are DISPLAY-ONLY in your UI.
     // Still save them so the backend stores what's shown in the UI.
     preferredDay: yourFormState.selectedDay as DayOfWeek | null,
     preferredTime: yourFormState.selectedTime || null, // ensure "HH:mm" format
   };
   savePref(payload);
 };
 // --- Populate your form fields on mount ---
 // When `pref` loads, set your form state from it:
 // e.g. setDeliveryMethod(pref?.channel ?? "EMAIL")
 //      setReminderEmail(pref?.notificationEmail ?? "")
 //      setReminderPhone(pref?.notificationPhone ?? "")
 //      setSelectedDay(pref?.preferredDay ?? null)   -- display only
 //      setSelectedTime(pref?.preferredTime ?? null) -- display only
 if (isLoading) return <p>Loading preferences…</p>;
 return (
   <div>
     {/* YOUR EXISTING UI — unchanged */}
     {/* Just wire in: */}
     {/*   - pref.channel → initial delivery method selection */}
     {/*   - pref.notificationEmail → Reminder Email Address input */}
     {/*   - pref.notificationPhone → Reminder Phone Number input */}
     {/*   - pref.preferredDay → SELECT REMINDER DAY (display-only, no save action) */}
     {/*   - pref.preferredTime → SELECT TIME (display-only, no save action) */}
     {/* "Reminders Paused" toggle — display-only, no API call */}
     {/* "Save Reminder Settings" button → calls handleSave() */}
     <button onClick={handleSave} disabled={isPending}>
       {isPending ? "Saving…" : "Save Reminder Settings"}
     </button>
     {isSuccess && <p>Settings saved!</p>}
     {isError && <p>Failed to save. Please try again.</p>}
   </div>
 );
}
IMPORTANT
Display-only fields — The reminder day, time, and "Reminders Paused" toggle shown in the screenshot are visible to owners but have no active scheduling function. They are still persisted via the PATCH call (so the owner sees their last selection) but the backend does not use preferredDay / preferredTime to actually schedule automated reminders at this time. Do not attach any scheduling logic to them on the frontend.

// utils/timeMap.ts
export const TIME_OPTIONS: { label: string; value: string }[] = [
 { label: "06:00 AM (Morning)", value: "06:00" },
 { label: "09:00 AM (Morning)", value: "09:00" },
 { label: "12:00 PM (Noon)", value: "12:00" },
 { label: "03:00 PM (Afternoon)", value: "15:00" },
 { label: "06:00 PM (Evening)", value: "18:00" },
 { label: "09:00 PM (Night)", value: "21:00" },
];
export const timeValueToLabel = (value: string | null): string =>
 TIME_OPTIONS.find((t) => t.value === value)?.label ?? value ?? "";

B3. Route 5 — POST /api/v1/owners/:id/availability-reminder
Purpose
Sends an availability reminder to the owner. Channel used = owner's saved preference by default, or override via channel in the body.
channel: "EMAIL" → sends HTML email
channel: "PHONE" → initiates Twilio voice call to owner's phone
channel: "BOTH" → email + phone call
Also always dispatches an in-app notification
Request
http
POST /api/v1/owners/clx00xyz.../availability-reminder
Authorization: Bearer <admin-token>
Content-Type: application/json
Request Body Schema
ts
{
 emailSubject?: string;   // defaults to "Please Update Availability Status for..."
 emailBody?: string;      // raw HTML — overrides the default template
 channel?: "EMAIL" | "PHONE" | "BOTH"; // override owner's saved channel
}
NOTE
All fields are optional. If omitted, backend uses the owner's saved ownerNotificationPreference.channel. If the owner has no saved preference, defaults to "EMAIL".

B8. Channel-Aware Send UI Pattern
The admin panel should:
Read owner.ownerNotificationPreference.channel from the GET response
Show the owner's channel badge (Email / Phone / Both)
Enable the relevant send button(s) based on that channel
Let admin optionally override by passing channel in the body
tsx
// Minimal wiring — drop into your existing admin owner detail component
import { useOwnerDetail, useSendAvailabilityReminder, useSendPaymentDueReminder } from "@/hooks/useAdminOwners";
export function AdminOwnerActions({ ownerId }: { ownerId: string }) {
 const { data: owner } = useOwnerDetail(ownerId);
 const channel = owner?.ownerNotificationPreference?.channel ?? "EMAIL";
 const { mutate: sendAvail, isPending: sendingAvail } = useSendAvailabilityReminder(ownerId);
 const { mutate: sendPayment, isPending: sendingPayment } = useSendPaymentDueReminder(ownerId);
 const handleAvailReminder = () => {
   // No channel override — use owner's own preference
   sendAvail({});
 };
 const handlePaymentReminder = () => {
   sendPayment({}); // backend auto-calculates due amount
 };
 const handleOverrideEmailOnly = () => {
   sendAvail({ channel: "EMAIL" }); // force email regardless of saved pref
 };
 return (
   <div>
     {/* Show owner's active channel — drives what buttons are active */}
     <span>Notification Channel: <strong>{channel}</strong></span>
     {/*  EMAIL  → show email icon active          */}
     {/*  PHONE  → show phone icon active          */}
     {/*  BOTH   → both icons active               */}
     {/* Availability reminder */}
     <button onClick={handleAvailReminder} disabled={sendingAvail}>
       {sendingAvail ? "Sending…" : "Send Availability Reminder"}
     </button>
     {/* Payment due reminder — only meaningful if owner has overdue payments */}
     {owner?.financials?.hasOverduePayment && (
       <button onClick={handlePaymentReminder} disabled={sendingPayment}>
         {sendingPayment ? "Sending…" : `Send Payment Reminder (${owner.financials.totalDue} ILS due)`}
       </button>
     )}
   </div>
 );
}
IMPORTANT
If ownerNotificationPreference is null (owner never saved prefs), the backend defaults to "EMAIL" and uses the owner's account email. Display "EMAIL (default)" in the admin UI in this case.

1. Global Concepts & Configuration
Base URL: http://localhost:5000/api/v1 (or your environment base URL)
Authentication: Most endpoints require Authorization: Bearer <accessToken>.
Walking Distance Calculation (walkingDistanceToNeighborhood):
Dynamic US & Israel Locations: Owners can select any coordinates for their apartment and neighborhood anywhere in the United States (e.g. Brooklyn, Monsey, Lakewood, Miami Beach, Chicago, Los Angeles) or Israel.
Priority Order for Calculation:
neighborhoodWalkingMinutes: If directly provided by the frontend (from Google Distance Matrix or owner input), it is used directly.
neighborhoodLat & neighborhoodLng: If the owner/frontend provides coordinates for the neighborhood center (e.g. from Google Places Autocomplete), walking time is calculated using Haversine formula (at 4.8 km/h).
Predefined Centroids: If neither is provided, falls back to the expanded built-in dictionary covering major Jewish communities in Israel and the US.
Targeted Destination Search (walkingDistanceToDestination):
When destLat, destLng, and walkingMinutes are supplied together, the API switches into Destination Mode.
In Destination Mode, standard text filters (city, neighborhood) are bypassed so users can search across neighborhood boundaries around any landmark.
